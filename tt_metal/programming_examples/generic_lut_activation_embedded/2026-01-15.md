# Work Summary - January 15, 2026

## Critical Bug Fix: Input Range Issue

### Problem Discovery
Test programs were using hardcoded `[-10, 10]` input range for all activations, causing numerical instability and huge errors for functions with limited safe ranges. For example, `logsigmoid` had >7000 relative error because it was being tested far outside its stable range.

### Root Cause Analysis
- **Test data generation**: Used hardcoded `[-10, 10]` regardless of activation function
- **LUT generation**: Correctly used activation-specific ranges from `activations_config.csv`
- **Mismatch**: Test inputs included values where activation functions overflow/saturate, causing artificially high error metrics

### Solution Implemented

#### 1. Created C++ Configuration Parser (`activation_config.hpp`)
New header file to parse `activations_config.csv` at runtime:

```cpp
struct ActivationConfig {
    std::string name;
    bool has_native_sfpu;
    float test_min, test_max;    // Safe range for testing
    float plot_min, plot_max;    // Range for visualization
    float full_min, full_max;    // Mathematical domain
    std::string description;
};

class ActivationConfigLoader {
public:
    static std::unordered_map<std::string, ActivationConfig> load_from_csv();
    static std::string extract_activation_name(const std::string& lut_filename);
    static std::pair<float, float> get_test_range(...);
};
```

**Key features:**
- Parses CSV without external dependencies (no Boost, no std::filesystem)
- Extracts activation name from LUT filename
- Returns per-activation test_range for input data generation

#### 2. Updated Test Programs

**Modified files:**
- `generic_lut_activation.cpp` (piecewise methods)
- `generic_lut_activation_native.cpp` (native SFPU)

**Changes:**
```cpp
// Load activation configuration to get test range
auto activation_configs = ActivationConfigLoader::load_from_csv();
auto [test_min, test_max] = ActivationConfigLoader::get_test_range(lut_filename, activation_configs);

// Create test input data using activation's test range
std::vector<bfloat16> input_data(elements_per_tile * n_tiles);
float test_range = test_max - test_min;
for (size_t i = 0; i < input_data.size(); i++) {
    float val = test_min + test_range * (i / float(input_data.size()));
    input_data[i] = bfloat16(val);
}
```

**Important distinction:**
- **Test range** (`test_min`, `test_max`): Safe input range for generating test data
- **Plot range** (`plot_min`, `plot_max`): Range used for LUT generation (stays at [-10, 10])
- **Kernels unchanged**: Still work with [-10, 10] LUTs, only host-side test data generation changed

#### 3. Example: `logsigmoid` Fix

**Before (hardcoded [-10, 10]):**
- Input: -10.0 → logsigmoid(-10) ≈ -10.000045 (saturated)
- Input: 10.0 → logsigmoid(10) ≈ -0.000045 (saturated)
- Mean relative error: >7000

**After (test_range [-1, 1]):**
- Input: -1.0 → logsigmoid(-1) ≈ -1.313 (in stable region)
- Input: 1.0 → logsigmoid(1) ≈ -0.313 (in stable region)
- Mean relative error: <1.0 (expected)

## Workflow Optimizations

### 1. Integrated Hardware Capture
**Previous workflow:**
1. Run sweeps for timing
2. Run `capture_hardware_outputs.sh` separately to dump CSVs
3. Total: 2× work

**New workflow:**
- Set `DUMP_OUTPUT_CSV` environment variable on last run only
- Capture happens inline during benchmark runs
- Total: 1× work (50% reduction)

**Implementation in sweep scripts:**
```bash
for run in $(seq 1 $NUM_RUNS); do
    if [[ $run -eq $NUM_RUNS ]]; then
        export DUMP_OUTPUT_CSV="${OUTPUT_DIR}/piecewise_constant_${activation}_${depth}.csv"
    else
        unset DUMP_OUTPUT_CSV
    fi
    # Run benchmark...
    unset DUMP_OUTPUT_CSV
done
```

### 2. Skip Least-Squares Piecewise Quadratic
**Rationale:**
- Remez algorithm produces minimax optimal approximations
- Least-squares is slower and worse (minimizes average error, not max error)
- No reason to run both

**Changes:**
- `sweep_piecewise_quadratic.sh`: Changed `LUT_TECHNIQUES=(least_squares remez)` → `LUT_TECHNIQUES=(remez)`
- `dashboard.py`: Removed `piecewise_quadratic` row (only show PQR)
- `pull_results.sh`: Added note about missing LSQ files, handle gracefully with `|| true`

### 3. Quick Run Configuration
**Changed:** `QUICK_RUN_DEPTHS="4 8 32"` → `QUICK_RUN_DEPTHS="32"`

**Rationale:**
- Depth 32 is representative of production use
- Depth 4/8 not production-relevant
- Faster quick validation cycles

## Technical Challenges and Solutions

### Challenge 1: Filesystem Header Not Available
**Problem:** `#include <filesystem>` compile error on servers

**Solution:** Rewrote path parsing using basic string operations:
```cpp
// Get just the filename without path
size_t last_slash = lut_filename.rfind('/');
std::string filename = (last_slash != std::string::npos)
    ? lut_filename.substr(last_slash + 1)
    : lut_filename;

// Remove .lut extension
size_t dot_pos = filename.rfind(".lut");
if (dot_pos != std::string::npos) {
    filename = filename.substr(0, dot_pos);
}
```

### Challenge 2: Binaries Not Rebuilding
**Problem:** After `git pull`, binaries existed but weren't rebuilt with new code

**Root cause:** CMake/Ninja sees existing binaries and skips rebuild

**Solution:** Manually touch source files to force rebuild:
```bash
touch tt_metal/programming_examples/generic_lut_activation/generic_lut_activation.cpp
touch tt_metal/programming_examples/generic_lut_activation/generic_lut_activation_native.cpp
cd build_Release
ninja $(ninja -t targets | grep 'programming_examples_generic_lut_activation' | cut -d: -f1)
```

### Challenge 3: Understanding Range Types
**Clarification achieved:**
- **test_range**: Safe input range for test data generation (e.g., [-1, 1] for logsigmoid)
- **plot_range**: Range for LUT generation, typically [-10, 10] for visualization
- **full_range**: Mathematical domain (e.g., [-inf, inf] for sigmoid)

**Key insight:** LUTs cover plot_range, test data uses test_range, kernels don't need to change.

## Lessons Learned

### 1. Always Validate Test Input Ranges
- Hardcoded ranges can hide bugs
- Per-activation validation is critical
- Test ranges should be in stable regions of functions

### 2. Centralized Configuration Pays Off
- 17+ shell scripts and 8+ Python scripts → 1 CSV file
- Easier to maintain and update
- Reduces configuration drift

### 3. Inline Instrumentation is Better
- Capturing outputs during benchmark runs (not separately) saves 50% time
- Environment variables are flexible way to control optional behavior
- Last-run-only capture avoids redundant work

### 4. Build System Understanding Matters
- CMake/Ninja may not rebuild after `git pull` if timestamps unchanged
- Manually touching source files forces rebuild
- Always verify binaries are actually rebuilt after code changes

### 5. Git Workflow for Remote Servers
- Commit and push directly from servers (don't rsync)
- Always `git pull --rebase` before pushing
- Use `git add -f` for gitignored result files when needed
