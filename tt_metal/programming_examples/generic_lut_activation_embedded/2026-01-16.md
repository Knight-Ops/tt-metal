# Work Summary - January 16, 2026

## Critical: SFPU Compiler Bug Discovery

### Problem: Loop Unrolling Failure in Piecewise Approximations

**Discovery:** Generic loop-based code for piecewise approximations compiles but produces incorrect results on hardware. The SFPU compiler fails to properly unroll loops with dynamic array indexing, leading to wrong segment selection and LUT lookups.

**Affected code pattern:**
```cpp
// This pattern FAILS on hardware (compiles but wrong results)
#pragma GCC unroll 16
for (uint32_t seg = 0; seg < NUM_SEGMENTS; seg++) {
    v_if (x < thresholds[seg]) {
        result = lut[seg * COEFFS_PER_SEG + 0] + ...;
    }
    v_endif;
}
```

**Symptoms:**
- Code compiles successfully with no warnings
- Wrong output values on device
- Different segments selected than expected
- Appears to be register allocation or loop unrolling bug in SFPU backend

### Extensive Debugging Journey (40+ commits)

**Attempts made:**
1. ✗ Pre-computing thresholds before loop (commits fb608ead89, f2e1cb8cc6)
2. ✗ Reducing register pressure (commit fb608ead89)
3. ✗ Changing array access patterns (commits 0fdfb71118, 565d429ded)
4. ✗ Reversing loop order (commit 565d429ded)
5. ✗ Pre-loading LUT values as vFloats (commit 330b1fde61)
6. ✗ Moving result assignment outside v_if blocks (commit b13a17fe8c)
7. ✗ Direct array indexing `lut[lut_base + 0]` (commit 4f112e0b0e)
8. ✗ Removing macros and using quadratic pattern (commit 70489a91f9)
9. ✗ Template specializations (multiple attempts)

**Final solution:** Hardcoded specializations for each depth

**Implemented in commits:**
- `6f32c1ae56` - Hardcoded specializations for piecewise_constant (depths 4, 8, 16, 32)
- `d0d579e93b` - Hardcoded specializations for piecewise_linear (depths 4, 8, 16)
- `4a9e116a4b` - Hardcoded specializations for piecewise_quadratic (all depths)
- `cf93633019` - Hardcoded specializations for piecewise_cubic (all depths)
- `cc0bb3b3c7`, `3157497318` - Removed depth=32 specializations (overkill)

**Workaround pattern:**
```cpp
// Hardcoded specialization that WORKS on hardware
template <>
inline void piecewise_constant_approx<4>(vFloat& result, vFloat x, const uint32_t lut[]) {
    vFloat t0 = lut[0], t1 = lut[1], t2 = lut[2], t3 = lut[3];
    vFloat v0 = lut[4], v1 = lut[5], v2 = lut[6], v3 = lut[7];

    v_if (x < t0) {
        result = v0;
    } v_elseif (x < t1) {
        result = v1;
    } v_elseif (x < t2) {
        result = v2;
    } v_elseif (x < t3) {
        result = v3;
    } v_else {
        result = v3;  // Clamp to last segment
    }
    v_endif;
}
```

## Technical Lessons Learned

### 1. SFPU Compiler Has Loop Unrolling Bugs
- Generic loop-based code compiles but produces wrong results
- Dynamic array indexing inside loops is unreliable
- Workaround: Hardcode specializations for each configuration
- Need to file bug report with minimal reproducing example

### 2. Hardware Testing is Critical
- Code that compiles may still be wrong on hardware
- Always test with CSV dumps and compare to expected values
- Debug prints are essential (when available)

### 3. Template Metaprogramming Has Limits
- C++ templates don't always translate well to SFPU backend
- Simpler is better: explicit code over clever generics
- Specializations are a necessary evil for hardware compilers

### 4. Visualization Iteration is Valuable
- 5 design iterations led to much better plot
- User feedback (even self-feedback) improves clarity
- Trade-off between information density and readability

### 5. Configuration Centralization Works
- Single CSV config file eliminates drift
- Scripts can dynamically adapt to config changes
- Reduces maintenance burden

### 4. Explore Non-Uniform Segment Boundaries 🔬 RESEARCH
**Goal:** Place more segments in high-curvature regions

**Current:** Uniform spacing (e.g., [-10, -5, 0, 5, 10] for depth=4)

**Proposed:** Curvature-based spacing
- More segments where f''(x) is large (high curvature)
- Fewer segments where f''(x) is small (nearly linear)
- Example: For sigmoid, dense around x=0, sparse at extremes

**Implementation challenges:**
1. Compute curvature (second derivative) of activation function
2. Distribute segment boundaries proportional to curvature
3. Pass boundary array to kernel (not just uniform step size)
4. Update kernel to use boundary array instead of computed thresholds

**Kernel changes needed:**
```cpp
// Current: uniform boundaries computed from range and depth
vFloat step = (input_max - input_min) / NUM_SEGMENTS;
vFloat threshold = input_min + seg * step;

// Proposed: non-uniform boundaries from LUT
vFloat threshold = lut_boundaries[seg];  // Passed as separate array
```

**Benefits:**
- Better accuracy with same number of segments
- More efficient use of memory budget
- Adaptive to function characteristics

**Concerns:**
- More complex LUT generation
- Larger LUT file (need to store boundaries)
- Kernel changes (may trigger SFPU compiler bugs again)
