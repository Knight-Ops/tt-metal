### Problem
When generating FP32 LUTs for higher-degree polynomials (octic depth 32), Sollya fpminimax produced coefficients with massive numerical cancellation:
- c0 = 909,958
- c1 = -819,848

These work correctly in float64 evaluation but produce catastrophic errors when evaluated in FP32.

### Root Cause
The MAE-based selection between Sollya and least-squares was evaluating in float64, hiding the FP32 rounding errors.

```python
# WRONG (original):
y_pred_sollya = sum(c * x_test**j for j, c in enumerate(coeffs_sollya))  # float64
mae_sollya = np.mean(np.abs(y_true - y_pred_sollya))
```

### Fix
Evaluate MAE in the target precision (FP32 or BF16) during coefficient selection:

```python
# CORRECT (commit efe0fd042d):
if self.mantissa_bits == 23:
    # FP32 evaluation
    coeffs_eval = np.array(coeffs_sollya, dtype=np.float32)
    x_test_eval = x_test.astype(np.float32)
    y_pred_sollya = sum(coeffs_eval[j] * x_test_eval**j for j in range(len(coeffs_sollya)))
    y_pred_sollya = y_pred_sollya.astype(np.float32)
```

### Result
FP32 LUTs now correctly select least-squares over Sollya when cancellation occurs:

**Before:**

**After:**

## Bug 2: BF16 Accumulation - Wrong Evaluation Semantics

### Problem
Hardware uses **BF16 accumulation** (quantizes after EVERY multiply-add operation), but our evaluation used FP32/FP64 accumulation, causing 30x MAE mismatch.

### Root Cause
Three evaluation paths had inconsistent precision handling:

| Path | Precision Behavior | Status |
|------|-------------------|--------|
| `sollya_bf16_remez.py` (coefficient selection) | FP32 accumulation | ✗ WRONG |
| `generate_piecewise_remez_luts.py` (LUT validation) | FP64 accumulation | ✗ WRONG |
| `plot_theoretical_error.py` (theoretical validation) | BF16 accumulation | ✓ CORRECT |

### Fix
Implement proper BF16 Horner's scheme with quantization after each operation in all paths:

**sollya_bf16_remez.py:**
```python
# WRONG (original):
y_pred_sollya = np.zeros_like(x_test_eval)
for j in range(len(coeffs_sollya)):
    y_pred_sollya += coeffs_eval[j] * (x_test_eval ** j)  # FP32 accumulation

# CORRECT (commit 4a4a4f0eb3):
y_pred_sollya = np.array([float(ml_dtypes.bfloat16(coeffs_eval[-1]))] * len(x_test_eval), dtype=np.float32)
for j in range(len(coeffs_eval) - 2, -1, -1):
    y_pred_sollya = y_pred_sollya * x_test_eval  # multiply
    y_pred_sollya = np.array([float(ml_dtypes.bfloat16(v)) for v in y_pred_sollya], dtype=np.float32)  # quantize
    y_pred_sollya = y_pred_sollya + coeffs_eval[j]  # add
    y_pred_sollya = np.array([float(ml_dtypes.bfloat16(v)) for v in y_pred_sollya], dtype=np.float32)  # quantize
```

**generate_piecewise_remez_luts.py:**
```python
# WRONG (original):
result = result * x_seg + coeffs_list[j][i]  # FP64 accumulation

# CORRECT (commit 4a4a4f0eb3):
for j in range(1, num_coeffs):
    result = result * x_seg  # multiply
    result = np.array([float(ml_dtypes.bfloat16(v)) for v in result], dtype=np.float32)  # quantize
    result = result + coeffs_list[j][i]  # add
    result = np.array([float(ml_dtypes.bfloat16(v)) for v in result], dtype=np.float32)  # quantize
```

## Bug 4: Coefficient Pre-Quantization in Horner Evaluation

### Problem
Found systematic mismatch between LUT generation and theoretical validation:
- `compute_accuracy_metrics`: MAE = 0.07334 (sigmoid octic depth 32 BF16)
- `evaluate_lut`: MAE = 0.1366 (86% higher!)

### Root Cause Analysis

**Issue 1: Coefficient Pre-Quantization in `plot_theoretical_error.py`**

The `evaluate_lut` function was pre-quantizing coefficients BEFORE Horner's scheme:

```python
# WRONG (pre-quantize coefficients):
if simulate_bf16:
    a8 = simulate_bf16_quantization(a8)  # Pre-quantize
    a7 = simulate_bf16_quantization(a7)
    # ...

# Then use pre-quantized values in Horner's scheme:
result = simulate_bf16_quantization(a8 * x_values)  # But a8 is already quantized!
result = simulate_bf16_quantization(result + a7)    # a7 is already quantized!
```

This meant:
1. Coefficients get quantized to BF16, then stored back as FP32 (with lost precision)
2. When used in arithmetic, these "quantized FP32" values give extra precision bits
3. Hardware behavior: coefficients are FULL FP32 until used in operations

**Issue 2: Incorrect Horner Initialization in `generate_piecewise_remez_luts.py`**

The `compute_accuracy_metrics` function was quantizing the highest coefficient BEFORE the first multiply:

```python
# WRONG (quantize coefficient before multiplying):
result = np.full_like(x_seg, coeffs_list[0][i])  # a8 (FP32)
result = np.array([float(ml_dtypes.bfloat16(v)) for v in result], dtype=np.float32)  # Quantize a8
# Then multiply:
result = result * x_seg  # Multiply quantized-a8 by x
result = np.array([float(ml_dtypes.bfloat16(v)) for v in result], dtype=np.float32)  # Quantize again
```

This quantized the coefficient twice:
1. Once before the multiply
2. Once after the multiply

But hardware only quantizes AFTER operations, not before.

### Fix

**Correct BF16 Horner Evaluation:**

```python
# CORRECT: Coefficients stay FP32, quantize only after each operation
if simulate_bf16:
    result = a8 * x_values  # FP32 coefficient × BF16 input = FP32 result
    result = simulate_bf16_quantization(result)  # Quantize to BF16
    result = result + a7    # BF16 + FP32 coefficient = FP32 result
    result = simulate_bf16_quantization(result)  # Quantize to BF16
    result = result * x_values  # BF16 × BF16 = FP32 result
    result = simulate_bf16_quantization(result)  # Quantize to BF16
    # ... continue for all coefficients
```

Applied to:
- `plot_theoretical_error.py`: All polynomial types (linear, quadratic, cubic, hexic, octic)
- `generate_piecewise_remez_luts.py`: Horner's scheme initialization

### Result

MAE values now match between generation and validation:

**Before:**
- `compute_accuracy_metrics`: MAE = 0.07334
- `evaluate_lut`: MAE = 0.1366
- **Difference: 86% (2x mismatch!)**

**After:**
- `compute_accuracy_metrics`: MAE = 0.07653
- `evaluate_lut`: MAE = 0.076533
- **Difference: <0.01% (matches!)**

### Key Insight

Hardware precision model:
1. **Coefficients**: Stored as FP32 in LUT file (NOT pre-quantized)
2. **Inputs**: Quantized to BF16 if LUT is BF16
3. **Operations**: Each multiply/add happens in FP32, result quantized to BF16
4. **NOT**: Quantize coefficients before use (wastes precision)

## Bug 5: Sollya Returns Zero for Sigmoid Extreme Segments (BF16)

### Problem Discovery

While investigating MAE discrepancies between hardware and theoretical validation, discovered that `piecewise_octic_remez_sigmoid_32_bf16.lut` has **ALL ZERO coefficients** for segments 1-8:

```
Segment 0 [-10.00, -9.38]: 9/9 non-zero (a8=1.095458e-07)
Segment 1 [-9.38, -8.75]: ALL ZERO ❌
Segment 2 [-8.75, -8.12]: ALL ZERO ❌
...
Segment 8 [-5.00, -4.38]: ALL ZERO ❌
Segment 9 [-4.38, -3.75]: 9/9 non-zero ✓
```

### Root Cause: Sollya's BF16 Precision Limitation

**Direct Sollya test** for segment 1:

```bash
# Input: sigmoid(x) = 1/(1+exp(-x)), range [-9.375, -8.75], degree 8, BF16 (7-bit mantissa)
# Output: p(x) = 0
# Max error: 1.5843e-4
```

Sollya literally returns `POLY: 0` (not even a coefficient array, just zero).

**Why?**

Sigmoid values in segments 1-8 are extremely small:
- sigmoid(-9.375) = 8.48e-5
- sigmoid(-8.75) = 1.58e-4
- sigmoid(-5.0) = 6.69e-3

With **BF16's 7-bit mantissa**, Sollya determines the best minimax approximation is simply **p(x) = 0**. The reported max error (1.58e-4) equals the maximum function value in that segment, confirming p(x)=0.

**Comparison with FP32**:

```bash
# Same segment with FP32 (23-bit mantissa):
# Output: 9 non-zero coefficients
# c0 = -1.334791e+06
# c1 = -1.144408e+06
```

FP32's higher precision allows Sollya to fit proper polynomials to these small values.

### Impact

**These zero coefficients were never caught** because:
1. Test range was [-5, 5] on Jan 17 (hardware outputs)
2. Test range changed to [-10, 10] on Jan 20 (activations_config.dat)
3. Segments 1-8 cover [-9.38, -5.0], which was never validated by hardware on Jan 17

**Current LUT status**:
- `piecewise_octic_remez_sigmoid_32_bf16.lut` - BROKEN (zero coefficients for 25% of segments)
- `piecewise_octic_remez_sigmoid_32_fp32.lut` - WORKING (all segments have proper coefficients)

### Fix Strategy

**Option 1: Use FP32 LUTs for sigmoid**
- Coefficients stored as FP32
- Hardware evaluates in FP32 arithmetic anyway (see Bug 6)
- Avoids Sollya convergence issues

**Option 2: Hybrid approach**
- Use FP32 precision for extreme segments (where sigmoid < 0.01)
- Use BF16 precision for middle segments (where sigmoid ≈ 0.5)
- Requires generator modification

**Option 3: Accept limited range**
- Document that BF16 sigmoid LUTs only work for [-5, 5]
- Use saturation for values outside this range
- Matches natural sigmoid behavior (saturates at 0 and 1)

## Bug 6: Hardware Uses FP32 Arithmetic, NOT BF16 Accumulation

### Critical Discovery

**CONTRADICTION**: Earlier analysis (Bugs 2, 3, 4) claimed hardware uses BF16 accumulation. This was **WRONG**.

### Evidence

**Test case**: Sigmoid octic depth 32, input x=9.5, segment 31 [9.38, 10.0]

**FP32 evaluation** (polynomial in float32):
```
Output: 0.9924
Ground truth: sigmoid(9.5) = 0.9999
Error: 0.0024 ✓
```

**BF16 evaluation** (quantize after EVERY operation):
```
Output: 1.125
Ground truth: sigmoid(9.5) = 0.9999
Error: 0.1251 ❌ (catastrophic!)
```

**Hardware output**:
```
Output: 0.988281 (BF16-quantized 0.9924)
Error: 0.0117 ✓
```

### Conclusion

Hardware performs:
1. Polynomial evaluation in **FP32 arithmetic** (Horner's scheme with FP32 accumulation)
2. **Final output** quantized to BF16 for storage/transmission
3. **NOT**: Quantizing after each multiply-add operation

### What Was Wrong?

The `--simulate-bf16` flag in `plot_theoretical_error.py` implements:
```python
# Horner's scheme with BF16 quantization after EACH operation
result = a8 * x
result = quantize_bf16(result)  # ← Extra quantization
result = result + a7
result = quantize_bf16(result)  # ← Extra quantization
# ...
```

But hardware does:
```python
# Horner's scheme with FP32 accumulation
result = a8 * x        # FP32
result = result + a7   # FP32
# ...
result = quantize_bf16(result)  # Only at the END
```

### Corrected Theoretical Validation

**WRONG** (was using):
```bash
python3 plot_theoretical_error.py --activation sigmoid --simulate-bf16
# MAE: 0.0114, Max: 0.1367
```

**CORRECT** (should use):
```bash
python3 plot_theoretical_error.py --activation sigmoid
# MAE: 0.0022, Max: 0.0120
```

The `--simulate-bf16` flag should NOT be used because hardware uses FP32 arithmetic, not BF16 accumulation.

### Result

**Before** (comparing FP32 hardware vs BF16-quantized theoretical):
- Theoretical MAE: 0.0114
- Hardware MAE: 0.0041
- **Mismatch: 2.8x**
- Theoretical had impossible values (>1.0 for sigmoid)

**After** (comparing FP32 hardware vs FP32 theoretical):
- Theoretical MAE: 0.0022

## Contradiction Resolution: BF16 Accumulation vs FP32 Arithmetic

**Earlier conclusion (Bugs 2-4):** Hardware uses BF16 accumulation (quantize after each operation).

**Current conclusion (Bug 6):** Hardware uses FP32 arithmetic (quantize only final output).

**Why the contradiction?**

The earlier "BF16 accumulation" fixes were comparing:
- Hardware (FP32 arithmetic) with BF16 output quantization
- Theoretical validation with `--simulate-bf16` (BF16 quantization after each operation)

This created artificial agreement between two WRONG approaches:
1. Theoretical was over-quantizing (quantizing after each op)
2. But we thought hardware was also over-quantizing
3. So they "matched" for the wrong reasons

**The truth:**
- Hardware: FP32 arithmetic + BF16 output quantization
- Theoretical (correct): FP32 arithmetic + optional BF16 output quantization
- Theoretical (wrong): BF16 arithmetic with quantization after each operation

**Lesson learned:** When two wrong implementations agree, investigate deeper. True validation requires understanding actual hardware behavior, not just matching numbers.
