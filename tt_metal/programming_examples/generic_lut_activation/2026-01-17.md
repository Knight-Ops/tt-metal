## 1. Embedded LUTs Implementation (10:29 AM - 2:48 PM)

### Motivation

**Problem:** JIT compilation overhead when loading LUTs from binary files
- Each kernel invocation must parse binary LUT file
- File I/O and parsing adds latency
- Not suitable for latency-critical applications

**Solution:** Embed LUT coefficients directly in kernel headers as C++ arrays

### Implementation Phases

#### Phase 1: LUT Header Generation Infrastructure (commit 0b1f59a806)
- Created `scripts/generate_lut_headers.py` to convert binary `.lut` files to C++ header files
- Generates `std::array<float, N>` with compile-time known sizes
- Output: `luts/headers/piecewise_<type>_<activation>_<depth>.hpp`

**Example generated header:**
```cpp
#pragma once
#include <array>

constexpr std::array<float, 16> piecewise_cubic_sigmoid_4_lut = {
    -0.044522f, 0.231059f, 0.000000f, 0.119203f,  // Segment 0: a, b, c, d
    -0.233480f, 0.000000f, 0.500000f, 0.500000f,  // Segment 1
    -0.233480f, 0.000000f, 0.500000f, 0.500000f,  // Segment 2
    -0.044522f, -0.231059f, 0.000000f, 0.880797f  // Segment 3
};
```

#### Phase 2: CMake Integration (commits b9ad85cc10, bef8e9432b, d147160fbd)
- Added `generate_lut_headers` custom target
- Created 522 binary targets: `generic_lut_activation_embedded_<type>_<depth>`
- Separated from original implementation to avoid conflicts
- Automatic header generation as part of build process

**CMake targets generated:**
```
generic_lut_activation_embedded_constant_4
generic_lut_activation_embedded_constant_8
generic_lut_activation_embedded_constant_16
generic_lut_activation_embedded_constant_32
... (522 total targets)
```

#### Phase 3: Kernel Modifications (commits 834b3c67aa, f566ef8125, 532f6aaf4d)
- Added `USE_EMBEDDED_LUTS` compile-time flag
- Modified all polynomial kernels to support both modes:
  - **File mode:** Load LUT from L1 memory (circular buffer)
  - **Embedded mode:** Use compile-time constant arrays

**Kernel pattern:**
```cpp
#ifdef USE_EMBEDDED_LUTS
    // Include generated header
    #include "luts/headers/piecewise_cubic_sigmoid_8.hpp"

    // Use compile-time constant
    constexpr auto& lut = piecewise_cubic_sigmoid_8_lut;
#else
    // Load from L1 memory at runtime
    auto p_lut = kutil::compute::memory::get_pointer_to_cb_data<lut_t>(cb_lut, 0);
    const auto& lut = *p_lut;
#endif
```

#### Phase 4: Host Code Simplification (commit db07842842)

## 4. Investigation: Remez Polynomial Coefficient Ill-Conditioning (4:30 PM - 4:35 PM)

### Problem Discovery

**Observation:** Hexic (degree 6) and octic (degree 8) Remez polynomials occasionally show **worse** MAE than cubic (degree 3), contradicting expectations.

**Affected cases (from hardware results):**
- `hardshrink` depth=4: Hexic 1.41× **worse** than cubic (MAE: 0.0605 vs 0.0430)
- `relu6` depth=8: Hexic 1.78× **worse** than cubic (MAE: 0.0118 vs 0.0066)
- `cosh` depth=8: Hexic 1.10× worse than cubic (MAE: 0.0424 vs 0.0384)
- `sinh` depth=8: Hexic 1.06× worse than cubic (MAE: 0.0433 vs 0.0410)

### Root Cause Analysis

**Initial hypotheses investigated:**
1. ❌ Poorly calculated Remez coefficients (OptimalPoly library bug)
2. ❌ SFPU hardware precision issues
3. ❌ Errors in kernel implementation (Horner's method evaluation)

**Actual root cause: ✅ Coefficient Ill-Conditioning**

For functions with sharp transitions or piecewise-linear regions, Remez produces mathematically optimal polynomials with **coefficient ranges spanning 15-20 orders of magnitude**.

**Example: `hardshrink` at depth=4**
```
Polynomial  | Coeff Range  | Max Coeff | Min Coeff     | MAE (HW)    | Status
------------|--------------|-----------|---------------|-------------|--------
Cubic       | 1.06 × 10^19 | 1.00      | 9.47 × 10^-20 | 0.0430      | OK
Hexic       | 1.45 × 10^17 | 8.57      | 5.93 × 10^-17 | 0.0605      | WORSE!
Octic       | 3.69 × 10^18 | 7.89      | 2.14 × 10^-18 | 0.0216      | Better
```

**Why this causes errors:**
- **Float32 precision:** ~7 decimal digits (IEEE 754)
- **Cannot accurately add** numbers differing by > 10^7
- **Horner's evaluation:** `result = a6*x^6 + a5*x^5 + ... + a0`
  - Tiny coefficients (10^-17) vanish when added to large results
  - More coefficients = more opportunities for ill-conditioning

**Why Remez isn't wrong:**
- Coefficients are mathematically correct for infinite precision
- Work perfectly in Python float64 (15 digits)
- Issue only manifests in hardware float32 (7 digits)

### Key Findings

**Pattern 1: Smooth functions benefit from higher degrees**
- Functions: `sigmoid`, `tanh`, `gelu`, `swish`, `sin`, `cos`, `erf`
- Result: 10-100× MAE improvement cubic → hexic
- Coefficient ranges: < 10^10 (well-conditioned)
- **Recommendation:** Use hexic or octic

**Pattern 2: Piecewise functions struggle with higher degrees**
- Functions: `hardshrink`, `relu6`, `hardtanh`, `threshold`
- Result: Non-monotonic MAE (hexic sometimes worse than cubic)
- Coefficient ranges: > 10^12 (ill-conditioned)
- **Recommendation:** Use cubic with more segments, or piecewise-linear

**Pattern 3: Rapidly growing functions (at higher depths)**
- Functions: `cosh`, `sinh`, `exp` at depth ≥ 8
- Result: Ill-conditioning emerges at higher depths
- **Recommendation:** Depth ≤ 8 use hexic, depth > 8 use cubic

### Decision Rules

**Coefficient range < 10^10:** Hexic safe ✅
**Coefficient range 10^10-10^12:** Hexic acceptable, monitor MAE ⚠️
**Coefficient range > 10^12:** Use cubic instead ❌

**Conclusion:** Kernel implementations are correct. Issue is fundamental numerical stability.
